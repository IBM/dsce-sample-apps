# Chat-Driven Workspace UI — Plan

## Overview

Pivot the app from a linear, screen-by-screen flow to a persistent **workspace layout** where the user can prompt Bob at any time and watch artifacts build up incrementally. The use case anchor is "Help me respond to this RFP" but the architecture is fully general — any document-to-artifact workflow fits.

The landing screen and investigation animation are unchanged. After the investigation completes, the app drops into a new **WorkspaceScreen** that replaces all the current output screens (discovered files, demo brief, demo plan, demo assets, demo ready).

---

## New Screen Flow

```
landing → investigating → workspace (persistent)
```

The workspace never navigates away. Everything happens inside it via chat prompts and tab additions.

---

## Tab Versioning Model

Every generation — including tweaks and edits — creates a **new versioned tab** rather than overwriting the previous one. This allows side-by-side comparison and makes the iterative improvement visible during a demo.

- `Context` is always the first tab and is never versioned or closeable
- Each artifact generation appends a new tab: `RFP Response v1`, `RFP Response v2`, `Presentation v1`, etc.
- The **latest version** of each artifact type is marked "Current" with a subtle badge and bolder tab style
- Older versions of the same artifact type are **dimmed** in the tab bar
- When 3+ versions of any artifact type exist, all but the latest collapse into a **history dropdown** on that artifact's tab group, keeping the tab bar clean
- The newly generated tab is automatically made active

## Data Source — `Box_Upload_Folder`

The mock data and documents for this demo live in a folder named **`Box_Upload_Folder`**. It exists in two places:

- **In the user's Box account** — the live source Bob reads through the Box MCP server (already set up by the user)
- **In this repo** at [`Box_Upload_Folder/`](Box_Upload_Folder/) — a local reference copy, confirmed by the user to be identical to the Box copy (generated by `scripts/generate-rfp-demo-assets.mjs` and `scripts/generate-mock-documents.mjs`)

Because the two copies match, the repo copy can be used to look up expected folder/file names while implementing, and as the basis for any offline fallback.

Contents of the folder (relevant to the RFP scenario):

| Subfolder | Role in the workspace |
|---|---|
| `Incoming RFPs/` | The RFP to respond to (`Acme Bank - RFP for AI-Powered Document Intelligence Platform.pdf`) |
| `Customers/Acme Corp/` | Customer context: Discovery Notes, RFPs & Proposals, Security & Compliance, Technical Specs, Workshop & Alignment |
| `Past RFP Responses/` | Reusable prior answers (Chase, Kaiser, Government) |
| `Product Documentation/`, `Security & Compliance Documents/`, `Pricing & Licensing/`, `Legal & Contract Language/`, `Implementation Methodology/`, `Case Studies & Customer Success Stories/` | Knowledge base used to ground RFP answers |
| `Generated RFP Responses/` | Example first-draft output (`.docx`, `.pdf`, `.txt`) — useful reference for the shape of the `RFP Response` artifact |
| `Acme_Late_Addendum_BAA_Compliance.pdf` (root) | Late addendum — a likely "gap / unclear item" for the Context tab |

**Known mismatch to resolve:** the current live loader [`scripts/box-live-documents.mjs`](scripts/box-live-documents.mjs) only reads a Box folder named `Acme Corp` (`ROOT_FOLDER_NAME`) and [`LiveBoxMcpProvider`](src/services/boxMcpService.ts:125) is documented as reading only that folder. The workspace needs the wider `Box_Upload_Folder` tree (Incoming RFPs, Past RFP Responses, product/security/pricing docs). See Sub-Task 0.
