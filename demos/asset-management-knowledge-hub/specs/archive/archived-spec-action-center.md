# Bob Specification — Action Center

## 1. Objective

Enhance the existing **IBM Maximo Knowledge Hub** application with a new top-level capability called **Action Center**.

The existing **Knowledge Hub** remains the primary conversational experience where a Reliability Engineer interacts with Bob.

The **Action Center** must be added as a **top-level navigation item at the same level as Architecture**, not as a child under Architecture.

Follow the actual image reference here architecture\action_center.png

Recommended left navigation:

- Knowledge Hub
- Data Ingestion
- Settings
- Audit Log
- Statistics
- Architecture
- **Action Center**

The Action Center is the persistent workspace for investigations, analyses, reports, recommendations, and tasks generated from conversations with Bob.

The core UX pattern is:

**Chat with Bob → Analyze → Generate Action → Create Dynamic Page → Review Evidence → Take Action**

Do not redesign the existing Knowledge Hub application. Extend the current IBM Carbon-based visual language and navigation.

---

## 2. Existing Knowledge Hub Experience

Keep the existing Knowledge Hub landing/chat page as the primary starting point for Reliability Engineers.

Users should be able to ask Bob questions such as:

> Show me the assets with recurring failures in the last 6 months and prioritize the ones we should investigate first.

Bob should retrieve and correlate relevant Maximo information such as:

- Asset master information
- Asset criticality
- Failure history
- Failure codes
- Work orders
- Downtime
- Preventive maintenance
- Job plans
- Maintenance history

Bob should respond conversationally with a concise summary.

When a response represents a significant investigation, analysis, report, recommendation, or task, do not place the complete result only inside chat.

Instead, Bob must create a persistent Action Center page.

---

## 3. Action Creation from Chat

Example Bob response:

> I found 15 assets with recurring failures in the last 6 months.
>
> I prioritized them using asset criticality, failure frequency, downtime, and recurring failure patterns.
>
> I've created a detailed investigation for you.

Display an IBM Carbon-style action card:

**Action created**

### Critical Asset Failure Investigation

15 assets analyzed

**Open in Action Center →**

Selecting the action must navigate directly to the generated investigation page.

---

## 4. Action Center Navigation

Add **Action Center** as a new top-level item in the existing left navigation.

It must be at the same hierarchy level as **Architecture**.

Example:

- Knowledge Hub
- Data Ingestion
- Settings
- Audit Log
- Statistics
- Architecture
- **Action Center**

Do not place Action Center inside the Architecture accordion or submenu.

Optionally display a small **New** indicator when Bob has recently generated a new action.

The Action Center must follow the application's existing IBM Carbon visual language.

---

## 5. Action Center Main Page

Page title:

# Action Center

Subtitle:

**Manage and track AI-generated investigations, analyses, reports, recommendations, and tasks.**

The page acts as the central workspace for everything generated by Bob.

Provide Carbon tabs:

**All | Investigations | Analyses | Reports | Recommendations | Tasks**

Include Carbon components for:

- Search
- Status filter
- Priority filter
- Asset filter
- Sorting
- Table/list view
- Pagination

Use a **Carbon Data Table** as the primary interaction model.

Avoid turning this page into a dashboard made primarily of cards.

---

## 6. Action Center Data Table

Recommended columns:

| Column | Description |
|---|---|
| Title | Name of generated action |
| Type | Investigation, Analysis, Report, Recommendation, or Task |
| Status | Draft, Running, Completed, In Review, Open, Closed |
| Priority | Critical, High, Medium, Low |
| Assets | Number of affected assets |
| Created | Creation timestamp |
| Source | Chat, System, or User |
| Actions | Context menu |

Example entries:

### Critical Asset Failure Investigation
**Investigation · Completed · High · 15 Assets**

Identified assets with recurring failures and prioritized them based on operational impact.

### Job Plan vs OEM Analysis
**Analysis · In Review · High · 7 Assets**

Compared current Maximo maintenance practices against OEM recommendations.

### Maintenance Gap Report
**Report · Completed · High · 7 Assets**

Detailed report covering identified maintenance gaps and supporting engineering evidence.

### Job Plan Review Tasks
**Tasks · Open · High · 4 Assets**

Reliability engineering review tasks generated from confirmed maintenance gaps.

---

## 7. Dynamic Action Pages

Every Action Center item can represent a dynamically generated page.

Bob should determine the appropriate page layout based on the type of analysis being performed.

Do not generate an identical generic page for every action.

Use reusable Carbon UI components but compose them dynamically based on the result.

Example:

### Critical Asset Failure Investigation

Possible tabs:

**Overview | Assets | Failure Patterns | Work Orders | Impact Analysis | Recommendations**

### Job Plan vs OEM Analysis

Possible tabs:

**Overview | Assets | Current Job Plans | OEM Recommendations | Gaps | Evidence | Recommendations**

---

## 8. Critical Asset Failure Investigation Page

When the user asks Bob to identify and prioritize failing assets, generate:

# Critical Asset Failure Investigation

Display a status indicator such as:

**Completed**

At the top provide Carbon metric tiles such as:

- **15** — Total Assets
- **78** — Failures
- **1,240 hrs** — Downtime
- **Estimated Operational Impact** — only when supported by source data

Do not fabricate impact values.

## 10. Continue Investigation Through Chat

The Action Center and Bob conversation must share context.

After creating the Critical Asset Failure Investigation, the user should be able to return to chat and say:

> Now check these assets against their OEM maintenance recommendations.

Bob must understand that **"these assets"** refers to the prioritized asset set from the previous investigation.

Do not require the user to select the assets again.

Bob should then retrieve:

### Maximo Operational Context

- Current job plan
- PM schedule
- Maintenance frequency
- Job plan tasks
- Inspection requirements
- Work order history
- Failure history

### Engineering Knowledge

- OEM manuals
- Maintenance manuals
- SOPs
- Engineering documentation
- Approved maintenance procedures

---

## 11. Job Plan vs OEM Analysis

Bob should semantically compare:

**What Maximo says we currently do**

against:

**What the OEM says should be done**

Evaluate areas including:

- Maintenance interval
- Inspection interval
- Maintenance activities
- Lubrication requirements
- Component replacement
- Measurements
- Tolerances
- Safety checks
- Inspection criteria
- Required procedures

Do not flag differences simply because wording is different.

Determine whether the difference represents a meaningful maintenance gap.

---

## 12. Generate Another Action

After the comparison, Bob should create another Action Center entry:

# Job Plan vs OEM Analysis

Example chat response:

> I compared the current Maximo job plans for the prioritized assets against the available OEM maintenance documentation.
>
> I found 7 assets requiring further review and 4 with significant maintenance differences.
>
> I've created a detailed comparison with supporting evidence.

Display:

**Action created**

### Job Plan vs OEM Analysis

**7 assets require review**

**Open in Action Center →**

## 13. Job Plan vs OEM Detail Page

The dynamically generated page should provide a clear comparison.

Use statuses such as:

### Aligned
Current maintenance practice is consistent with the retrieved OEM guidance.

### Review Required
A potential difference exists and requires reliability or engineering validation.

### Gap Identified
Available evidence indicates a meaningful difference between the current maintenance practice and OEM guidance.

For every asset provide:

- Asset
- Criticality
- Current Maximo job plan
- Current maintenance interval
- OEM recommendation
- OEM recommended interval
- Identified difference
- Reliability impact
- Recommended action
- Evidence
- Source document

---

## 14. Evidence and Explainability

Evidence and explainability are mandatory.

When the user selects an identified gap, provide an evidence view or Carbon side panel.

Structure the information around three questions.

### What happened?

Show operational evidence:

- Failures
- Failure patterns
- Work orders
- Downtime
- Maintenance history

### What should have happened?

Show engineering evidence:

- OEM recommendation
- Maintenance procedure
- Recommended interval
- Relevant SOP or manual
- Source reference

### What should we do next?

Show Bob's recommended action.

Clearly distinguish:

- **Operational Data**
- **Retrieved Engineering Knowledge**
- **AI Analysis**
- **Recommended Action**

Bob must never represent AI-generated reasoning as an OEM requirement.

---

## 15. Create Reliability Tasks

From an analysis page, allow the Reliability Engineer to select:

**Create Tasks**

Bob can create tasks such as:

### Review Job Plan — P-101

**Priority:** High

**Reason:** Current lubrication interval differs from the retrieved OEM recommendation.

Include:

- Asset
- Current job plan
- Existing maintenance practice
- OEM recommendation
- Identified gap
- Supporting evidence
- Recommended change
- Priority
- Owner
- Status

These tasks must automatically appear under:

**Action Center → Tasks**

## 16. Maintain Traceability

Every generated object must maintain lineage.

Example:

**Chat**

↓

**Critical Asset Failure Investigation**

↓

**Job Plan vs OEM Analysis**

↓

**Maintenance Gap Report**

↓

**Job Plan Review Task**

A Reliability Engineer must be able to navigate backward and understand:

- Which conversation initiated the investigation
- Which assets were analyzed
- Which operational data was used
- Which engineering documents were retrieved
- What Bob concluded
- Why an action was recommended

---

## 17. Action Lifecycle

Support a lightweight lifecycle.

### Investigations / Analyses

**Running → Completed → In Review → Closed**

### Tasks

**Open → In Progress → Completed → Closed**

### Recommendations

**Proposed → Accepted → Rejected → Implemented**

Use Carbon status tags consistently.

Bob must not automatically mark an engineering recommendation as accepted or implemented.

Human validation is required.

---

## 18. Dynamic UI Principle

A key capability of the application is that **Bob can create UI experiences as part of the conversation**.

The UI must not be limited to predefined static reports.

Bob should be able to dynamically compose pages from approved reusable Carbon components such as:

- Data tables
- Metric tiles
- Tabs
- Accordions
- Structured lists
- Tags
- Progress indicators
- Charts
- Evidence panels
- Side panels
- Modals
- Notifications

Bob determines the page composition based on the user's request and resulting data.

Every generated page must remain consistent with the application's IBM Carbon design system.

---

## 19. UI/UX Design Requirements

Follow **IBM Carbon Design System** patterns throughout.

Maintain the visual language of the existing Maximo Knowledge Hub application.

Use:

- Existing dark application header
- Existing dark left navigation
- White/light content canvas
- IBM Carbon typography
- Carbon spacing conventions
- Carbon Data Tables
- Carbon Tabs
- Carbon Tags
- Carbon Buttons
- Carbon Search
- Carbon Dropdowns
- Carbon Overflow Menus
- Carbon structured lists
- Carbon side panels
- Carbon loading states and skeletons

Use IBM blue primarily for:

- Active navigation
- Links
- Primary actions
- Selected tabs
- Important interactive elements

Avoid excessive gradients, rounded consumer-style cards, decorative illustrations, or generic AI-dashboard styling.

The experience must look like an extension of an **IBM enterprise application**, not a separate AI application.

---

## 20. Knowledge Hub vs Action Center

The two experiences serve different purposes.

### Knowledge Hub / Bob Chat

Used for:

- Asking questions
- Exploring data
- Requesting investigations
- Refining analysis
- Giving instructions
- Asking follow-up questions

### Action Center

Used for:

- Persistent results
- Investigations
- Detailed analysis
- Reports
- Recommendations
- Evidence
- Reliability tasks
- Tracking progress

The user should move seamlessly between them.

## 22. Final Experience

The application should demonstrate a shift from a traditional:

**Chatbot → Answer**

experience toward:

**Conversation → Investigation → Evidence → Dynamic Experience → Recommendation → Human Action**

Bob becomes the intelligent experience and orchestration layer connecting:

**Maximo Operational Context + Engineering Knowledge + AI Reasoning + Dynamic Carbon UI + Reliability Actions**

The goal is for a Reliability Engineer to start with a natural-language question and finish with a **prioritized, evidence-backed, and actionable reliability improvement**, without manually navigating multiple Maximo screens, reports, OEM manuals, and engineering documents.
